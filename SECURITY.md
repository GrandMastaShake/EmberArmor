# Security Policy

EmberArmor is a prototype and is not ready for use as a security control. Do not rely on it to protect a system. Current status is in [README.md](README.md).

## Supported versions

Only the default branch (`master`) is supported. There are no tagged releases.

## Reporting a vulnerability

Use GitHub's private vulnerability reporting (Security tab, Report a vulnerability). Please do not put exploit details in a public issue.

## What the code does today

Checked against the code on 2026-10-02 (the items on directory scopes, on exceptions, on relative paths and on reminders on 2026-10-05, the last of them again after an independent test of the reminders that day):

- Every route except `GET /ready` requires `Authorization: Bearer <EMBER_API_KEY>`. A missing, malformed or wrong key gets 401. The comparison uses `hmac.compare_digest`.
- Start-up fails unless `EMBER_API_KEY` and `EMBER_TOKEN_SECRET` are set and at least 32 characters each. A `.env` file is read only when `EMBER_ENV=development`.
- Rate limiting is in memory, per peer address, 60 requests per 60 seconds by default. Start uvicorn with `--no-proxy-headers`; without it, uvicorn takes the peer address from `X-Forwarded-For` on connections from 127.0.0.1 and a local client can sidestep the limit.
- `/docs`, `/redoc` and `/openapi.json` are switched off.
- `.gitignore` excludes `.env`, `*.pem` and `*.key`. A scan of the git history found no provider API keys and no private keys.
- The constraint ledger gate (`ember-gate`, `ember_armor/ledger`) can only restrict: there is no `allow` effect, the Claude Code hook never prints `allow`, and a ledger shipped inside a repository cannot grant anything. A rule nobody has confirmed on this machine can do no more than warn.
- The gate has three modes. In `observe` mode (the default) the hook prints nothing. In `remind` mode it never blocks and never asks; when a rule fires it hands the agent the rule in its own words, as `additionalContext` with no permission decision. In `enforce` mode `ask` and `deny` take effect, and a decision that does not block is a reminder. A reminder grants nothing and blocks nothing.
- What the hook prints quotes only text the owner vouches for: the built-in pack, rules of the user ledger with `"confirmed": true` (the file named by `EMBER_LEDGER` counts as the user ledger), and rules of a project ledger confirmed on this machine by id and content hash. A rule nobody confirmed adds nothing to what the hook prints, in any mode: not its text, not its source, not its id, not a count, and not a line in the reason of a blocking decision. It stays in the audit log. The reason is that the agent reads what the hook prints as coming from the owner. A project ledger travels with a repository, so without this rule a cloned repository could put its own instructions in front of the agent by shipping a rule that fires. `EMBER_LEDGER` must name an absolute path: a relative one would be looked for in the directory of the call, which a repository chooses, and is refused.
- Quoted text is put on one line, without characters that do not show (control and format characters, private-use and unassigned code points, lone surrogates, variation selectors, the filler and blank code points listed in the specification, and combining marks after the fourth in a row), with double quotes turned into single ones, and capped: a rule's text at 400 characters, its source at 120, a reminder at 1,500, the summary at the start of a session at 3,000. The last line is always the same fixed sentence. Nothing of the call (no command, no path, no argument) goes into a reminder. The text and source quoted in the reason of a blocking decision are sanitised the same way.
- The hook does not print why a project ledger could not be loaded, because that reason can quote the file (a rule id, a field name), and it does not print the file's path, because the names of a repository's directories are the repository's words too. It prints fixed words. A project rule that could not be evaluated is reported in fixed words as well, without its id. The reason, the path and the id stay in the audit log and in what `ember-gate check`, `ember-gate rules list` and `ember-gate lint` print.
- A repository cannot switch the owner's rules off by shipping something broken. Each ledger is loaded on its own and each rule is judged on its own: a project ledger nobody can parse, or a rule whose evaluation raises, is a gate failure (an `ask` in `enforce` mode), and the built-in pack and the user ledger are still evaluated, so their `deny` stands and `remind` mode still reminds. A glob with a malformed character class is literal text and raises nothing.
- The same rule is reminded at most once per session and interval (15 minutes unless configured), and the audit entry records what each reminder quoted. A project rule and a user rule with the same id are limited apart. The limit starts again when a session starts after a compaction or a clear. A reminder the audit log could not record is not sent, and neither is a session-start summary. A field the log cannot encode (half of a surrogate pair) is written as its escape, and a line of the log that cannot be read is passed over, so neither stops the logging or the reminders.
- `ember-gate hook` exits 0 whatever its arguments and input are. Arguments it does not know are a gate failure (an `ask` in `enforce` mode), not a usage error: exit status 2 would block the call on the host. That holds for a line with options in front of `hook` too. The session-start hook never fails the session: a ledger that cannot be loaded takes only its own rules out of the summary, and on any other error it prints nothing.
- A rule scoped to a directory or a repository is judged for each command of a shell call, on the directory in effect when the command runs (`cd`, `pushd`, `git -C` and the like are followed). A directory the gate cannot read from the command string counts as in scope, so an unreadable `cd` does not lead out of a rule. Neither does a `cd` that may not have run (behind `||`, behind `&&` after a command that can fail, in a branch, in a loop, in a function that is called): the directory after it is unknown. A call that names no working directory is in an unknown directory as well.
- Exceptions to rules exist only in the owner's `~/.ember/config.json`. A ledger cannot hold one, so a repository cannot ship one, and a `config.json` inside a repository is never read. Each exception must name a directory, a repository or a condition and give a reason; a whole filesystem or drive is refused as a directory. The two built-in deny rules and the rules that guard the gate's own files, rules, variables and host settings take no exception. A directory the gate cannot read, or cannot be sure of, gains none. For a rule that looks at paths an exception reaches only the paths in its own directories: `rm -rf ~/Documents` run in a directory where recursive deletes are excepted is still asked about. Each use is recorded in the audit log. A malformed exception is a configuration failure: no exception is taken from that file.
- If the gate itself fails (unreadable ledger or configuration, a repository lookup that is refused or raises, unreadable hook input, internal error), then in `enforce` mode the decision is `ask` with the error as the reason, never silent approval and never a hard block; in `observe` and `remind` mode the call proceeds and the error is logged.
- Shell input the gate cannot read in full is marked and asked about, never dropped. More than 32 stacked wrappers, a command string over 200,000 characters, more than 2,000 commands, a brace expansion to more than 64 words or a relative path to resolve against more than 9 possible directories are parse errors.
- A delete or a write with a relative path is judged in every directory it may happen in: after a `cd` that may not have run, both where the `cd` leads and where the shell was (`[ -d /tmp/x ] && cd /tmp/x; rm -rf src` is asked about). Paths inside a nested shell that is started in another directory (`env -C dir sh -c '...'`, `pwsh -WorkingDirectory dir`) are resolved there, so the rules on the gate's own files and on protected directories see them.
- In `enforce` mode the gate asks before an agent writes to or deletes its configuration, ledgers or audit log, confirms or removes rules through `ember-gate`, sets `EMBER_GATE_MODE`, `EMBER_LEDGER`, `EMBER_HOME`, `EMBER_GATE_BUILTIN` or `EMBER_GATE_REMIND_INTERVAL` in a command, or edits the Claude Code settings files that hold the hook. In `remind` mode the same calls get a reminder of that rule and proceed; in `observe` mode they are logged.
- Every gate evaluation goes to a hash-chained audit log under `~/.ember/audit/`, with secret-shaped values replaced before writing. An entry names the rules its reminder quoted, and a summary printed at the start of a session is an entry of its own, so what the hook told the agent can be read back. `ember-gate log verify` detects edits, removed entries and a deleted month file. It is not proof against someone with write access who recomputes the chain.
- The HTTP ledger routes take no file path from a request and never look for a project ledger. Load and gate failures are answered in fixed words; the details go to the server log.

## What it does not do

- The detector is four regular expressions. It passes plain prompt-injection text as `SAFE`.
- The gate is built for good-faith agents that drift. An agent that deliberately obfuscates a command (a program named by a variable the gate cannot resolve, `eval` of an expansion, code run through `python -c`) can get past the built-in pack; those forms are marked, and a user rule on `dynamic_shell` can ask about them. The gate also never sees work done inside a tool the host does not report.
- The directory a command runs in is read from the command string and never checked against the machine. A `cd` that fails, a `cd` run in the background, `GIT_DIR` in the environment, a `cd` inside a script the shell sources or behind an alias, a command in the body of a function that is called somewhere else, or the directory option of a program the gate does not know (`tar -C`, `go -C`) can make a directory-scoped rule miss a command, or let an exception cover one that runs elsewhere.
- An exception on a rule that looks at a command alone is judged by where the command runs, not by what it is aimed at: with `builtin.delete.mirror` excepted under a directory, `rsync --delete` from there to anywhere is not asked about.
- A reminder is told to the agent, not enforced. The agent can read it and make the call anyway; in `remind` mode a rule with effect `deny` blocks nothing, and the gate cannot tell whether a reminder was heeded. What a host does with `additionalContext` is the host's business: the owner checked it on his Claude Code on 2026-10-05 with a probe hook, and the tests here check only what the hook prints.
- Confirming a rule vouches for its words. A confirmed rule is quoted to the agent as the owner's instruction; the sanitiser removes what does not print and caps the length, it does not judge what the text says. Read a project rule before confirming it.
- In `remind` and `observe` mode nothing stands between an agent and the confirmation itself. An agent can run `ember-gate rules confirm ID --project` or write `project-confirmed.json` in the Ember home; in `remind` mode it is reminded of the rule that guards the gate and the call proceeds, and from then on the project rule is quoted as one the owner confirmed. The trust rule above therefore holds against a repository on its own, not against an agent that does what a repository's instructions say. Only `enforce` mode asks first, and `ember-gate rules confirm` does not check that a person is at the terminal.
- A `config.json` with a wrong value or an unknown key makes the gate ask on every call, whatever mode the file names, and so does a copy of the gate from before reminders that reads `remind`, `remind_interval_minutes` or `announce_on`. Update the installed gate before writing those settings, and run `ember-gate check` after editing the file.
- The limit on reminders goes by session id. Whether Claude Code gives the calls of subagents the id of the main session has not been checked; if it does, a reminder one of them received holds the rule back for the others during the interval.
- The reason a project ledger could not be loaded is kept out of what the hook prints, not out of the audit log or of `ember-gate check`. An agent that reads the log or runs the command reads the file's words there, as it could by opening the ledger file. Errors in the owner's own files (the user ledger, `config.json`, the confirmation record) are printed in full.
- The limit on reminders is read before the entry of the call is written: two calls proposed at the same moment can both be reminded of the same rule.
- Redaction in the audit log is by name and shape. A secret with an unremarkable name and shape, passed where nothing marks it, reaches the log.
- The service has no audit log of its own: `AuditLogger` in `ember_armor/security/` exists, but no route calls it.
- JWT signing (`ember_armor/security/tokens.py`) and PBKDF2 key derivation (`ember_armor/security/crypto.py`) exist with tests, but no route uses them.
- There is no Dockerfile and no container configuration in this repository.
- `ember_proxy/` is an experimental sketch that does not work. Its installer and launcher scripts were removed on 2026-10-05; they remain in the git history. The installer added a mitmproxy root certificate to the machine-wide Windows Trusted Root store and the launcher ran `git pull` on every start. `ember_proxy/addon.py` still carries a hardcoded default API key. If you ran the installer from an earlier commit, follow the removal steps in [ember_proxy/README.md](ember_proxy/README.md).

Other known weaknesses are listed under Known issues and Known limits in the README, and in [docs/constraint-ledger.md](docs/constraint-ledger.md).
