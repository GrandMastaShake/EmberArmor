## 1. A trailing dot on Windows slips past the host-settings rule

Microsoft patched a Copilot flaw (CVE-2026-103572) where a file name ending
in a dot, such as ".mcp.json.", got past a check that stopped the agent from
editing its own config files. Windows drops the trailing dot and opens the
same file, so the agent could change its own MCP config and run commands,
also through indirect prompt injection.

EmberArmor has the same hole. On master, with the Windows flavour, a Write to
.claude\settings.json fires builtin.gate.host-settings (ask), but a Write to
.claude\settings.json. or .claude\settings.local.json. fires nothing, and
neither does the NTFS default-stream form .claude\settings.json::$DATA or a
PowerShell Set-Content on the dotted name. Those files hold the hook that runs
the gate. The cause is in ember_armor/ledger/paths.py normalize(): it strips a
trailing space but keeps a trailing dot and a "::$DATA" suffix. The .ember
directory rule (builtin.gate.files) still fires, because it matches "under" a
directory, not a file name.

Separately, a Write to .mcp.json, to .claude/hooks/ or to .vscode/tasks.json
fires no rule today. Each is a file that trusted host software later runs.

- Source: https://adversa.ai/blog/top-ai-coding-agent-security-resources-november-2026/ (Nov 2 2026)
- Area / tool: gate; Write, Edit, MultiEdit, PowerShell (Windows only)
- Could a rule catch it: yes, once paths normalize the way Windows does
- Smallest change: in normalize() for the Windows flavour, drop trailing dots
  and spaces from every segment and a trailing "::$DATA" stream name; add
  must_flag cases (Write and PowerShell to the dotted and stream forms of both
  settings files) and a near miss (a file really named settings.json.bak).
  This touches no rule, but it guards the gate's own hook, so it needs a close
  review.

## 2. ruflo MCP bridge ran terminal commands for anyone on the network

ruflo, an agent harness, shipped a default Docker Compose setup whose MCP
bridge listened on all interfaces without authentication. Its tool blocklist,
which named the terminal tool, was only enforced on the autopilot path, so a
direct MCP tool call through the bridge reached the terminal tool and gave a
shell in the container, with the provider API keys in its environment. Fixed
in 3.16.3 (CVE-2026-59726, GHSA-c4hm-4h84-2cf3): loopback by default, bearer
auth, terminal execution opt-in.

The lesson for EmberArmor is the blocklist one: a rule that holds on one path
to a tool and not another. EmberArmor parses commands only for the four shell
tools it knows (Bash, PowerShell, mcp__Windows-MCP__PowerShell,
mcp__terminal__run_in_terminal). Any other MCP server that runs a shell
command is in "mcp__* (other MCP tools): unwatched", so none of the shell
rules reach it.

- Source: https://dev.to/facilishz/ruflos-default-mcp-bridge-exposed-terminal-execution-to-the-network-5caf (Nov 27 2026)
- Area / tool: mcp__* (other MCP tools): unwatched
- Could a rule catch it: partly. The open network port is outside the gate.
  An agent calling some other MCP terminal tool is not, but today nothing
  watches it.
- Smallest change: a graph gap entry or an "ask" rule for MCP tools whose
  input has a "command" argument and whose server is not one of the known
  shell tools, so a new terminal-like MCP tool is asked about, not ignored.

## 3. Claude Code's "don't ask again" file leaks secrets into repos

Apiiro found that when a user approves a shell command with "Yes, and don't
ask again", Claude Code saves the exact command, including any token or
password typed in it, to .claude/settings.local.json. The ignore rule for that
file lives in the user's global git excludes, not the project's .gitignore,
so it is often committed (over a thousand public repos held a live-looking
secret, some committed by the agent itself). GitGuardian later reported far
more. The advice is to rotate, untrack the file, add it to the project's
.gitignore and stop typing secrets into commands.

On master, builtin.gate.host-settings asks before writing that file, but
staging or committing it (git add .claude/settings.local.json, or git add -A
when it is not ignored) fires nothing, and neither does a command carrying a
bearer token in a header.

- Sources: https://thehackernews.com/2026/11/claude-codes-dont-ask-again-file.html (Nov 7 2026);
  https://www.infoq.com/news/2026/11/claude-code-leaking-secrets/ (Nov 22 2026)
- Area / tool: git, secrets; Bash, PowerShell
- Could a rule catch it: partly. A rule can ask before a git add that names a
  .claude settings file. A blanket "git add -A" cannot know whether the file
  is ignored, and secrets typed into commands are the user's own input.
- Smallest change: an "ask" rule on git add / git stage naming
  **/.claude/settings*.json, with a must_flag case and a near miss
  (git add of an ordinary file).

## 4. Microsoft agent-framework on PyPI shipped a .pth credential stealer

Versions 1.26.1 and 1.26.2 of Microsoft's agent-framework package, published
Nov 17 through a compromised publisher account, dropped a .pth file into
site-packages. Python runs a .pth line at every interpreter start, so the
stealer ran even when the package was never imported, and collected cloud,
git, package manager and Hugging Face credentials and CI tokens.

The install itself is outside the gate. But an agent writing a .pth file into
a site-packages folder is a strong signal of the same persistence trick, and
on master a Write to .../site-packages/x.pth fires nothing.

- Source: https://www.chainguard.dev/unchained/microsoft-agent-framework-compromised-on-pypi-november-2026 (Nov 17 2026)
- Area / tool: Write, Edit, Bash (path write)
- Could a rule catch it: partly (the write, not the poisoned install)
- Smallest change: an "ask" rule on path writes matching
  **/site-packages/*.pth and **/dist-packages/*.pth, with must_flag cases for
  Write and a shell redirect, and a near miss (reading a .pth file).

## 5. AWS API MCP Server: a deny list that never matched

AWS's API MCP Server let operators deny or require confirmation for AWS
operations, but it normalized operation names wrongly, so names with several
capital letters in a row never matched a correctly written deny entry. Fixed
in awslabs.aws-api-mcp-server 1.5.1 (CVE-2026-125271, GHSA-4wq9-grf3-qg2p).

This is the same class of bug as finding 1: a rule that is right on paper and
silently misses because the input was not brought to one form first.
EmberArmor already normalizes paths and command names; finding 1 shows one
Windows form it misses.

- Source: https://aws.amazon.com/security/security-bulletins/2026-176-aws/ (Nov 10 2026)
- Area / tool: all path and command rules
- Could a rule catch it: not a rule; a test
- Smallest change: a test that, for every built-in path glob that names a
  file, also checks the Windows aliases of that file (trailing dot, trailing
  space, default stream, other letter case) fire the same rule.
